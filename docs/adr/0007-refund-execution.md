# ADR 0007 — اجرای استرداد وجه با تأیید ادمین و ماشینحالت امن

**تصمیم:** استرداد فقط با اقدام ادمین، claim اتمیک، نتیجهٔ مبهم ⇒ REVIEW بدون تکرار خودکار، درگاههای بدون API ⇒ MANUAL با ثبت مرجع، سقف مبلغ و نهاییبودن در تریگر DB، Audit کامل.
**چرا نه job ی خودکار؟** حرکت پول بدون API ی ایدمپوتنت؛ خطای اجرای مجدد گرانتر از تأخیر چند ساعته است.
**جایگزینهای ردشده:** تلاش مجدد خودکار پس از timeout (خطر استرداد دوباره)؛ تغییر `Payment.status` فقط پس از PROCESSED (ریسک شکستن منطق هماهنگی نوبت/ترمیم؛ بهجایش معنای status مستند شد).
**پیامد:** مهاجرت `phase13-refunds.sql`؛ توکن دسترسی زرینپال راز جدید؛ دو فرض زرینپال باید در sandbox راستیآزمایی شود.

## الحاقیه ۱۴۰۵/۹/۱ — استرداد خودکار اختیاری (M4)

تصمیم اصلی پابرجاست: اجرای پیشفرض، دستی و با تأیید ادمین است. با این حال قابلیت **اختیاری** استرداد خودکار تحت شرایط سختگیرانه اضافه شد:

- فقط با `FF_M4_FINANCE_AUTO=true` **و** `ENABLE_WORKERS=true` فعال میشود (پیشفرض: خاموش — fail-closed).
- worker فقط refundهای `PENDING` بالغتر از `REFUND_WORKER_MIN_AGE_MIN` و با `tryCount < REFUND_WORKER_MAX_TRY` را میگیرد.
- تمام مسیرها از همان `RefundService.execute` عبور میکنند: claim اتمیک، RLS، Audit و Outbox؛ بدون پیادهسازی موازی.
- تأیید دو نفره (dual approval) دور زده نمیشود: `canConsume` پیش از هر تماس درگاه، تأیید معتبر همان اقدام را لازم دارد.
- نتیجهٔ مبهم ⇒ `REVIEW` و **هیچ retry خودکاری**؛ GatewayErrorها توسط همان منطق مدیریت میشوند.
- `sweepStale` از `list()` جدا و به worker سپرده شد تا PROCESSING گیرکرده زودتر به REVIEW برود.
- جدول قواعد بازپرداخت (`scheduling/refund-policy.ts`) جای magic numberها را گرفت و قابل نمایش در شبیهساز M2 است.

**شرط پذیرش عملیاتی:** قبل از روشن کردن flag در production، تأیید ایدمپوتنتی `AddRefund` در sandbox زرینپال و تست `refund-worker.int.test.ts` الزامی است.
