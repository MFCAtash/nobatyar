# ADR 0008 — سخت‌سازی بک‌اند (فاز ۱۷)

وضعیت: پذیرفته‌شده

## زمینه
بررسی فاز ۱۴ چند ریسک را نشان داد: توکن دسترسی تا انقضا معتبر می‌ماند؛ endpoint های مالی در برابر تلاش مجدد/کلیک دوباره محافظ نداشتند؛ اعلان‌ها بعد از commit و بیرون از تراکنش ساخته می‌شدند (مرگ پروسه ⇒ اعلان گم)؛ یک ادمین می‌توانست به‌تنهایی پول را جابه‌جا کند؛ مستند API وجود نداشت.

## تصمیم‌ها
1. **sid + ابطال Redis.** `sid` = `familyId` ی refresh. دو کلید کوتاه‌عمر: `rev:sid:<sid>` و `rev:uid:<userId>` (cutoff). TTL = عمر access token + ۶۰ث ⇒ حافظه محدود. Redis ناپایدار ⇒ ۵۰۳ (fail-closed؛ در production قابل تغییر نیست). WebSocket هر ۳۰ث و SSE هر heartbeat دوباره می‌سنجند (خطای Redis ⇒ اتصال می‌ماند).
2. **Idempotency-Key در Postgres** (نه Redis): ماندگاری و رقابت‌ایمنی با `INSERT … ON CONFLICT DO NOTHING`. فقط ۲xx ذخیره می‌شود؛ خطا ⇒ قفل آزاد. همان کلید + درخواست دیگر ⇒ ۴۲۲؛ هم‌زمان ⇒ ۴۰۹ + Retry-After. `verify` ی درگاه اختیاری است (poll می‌شود).
3. **Outbox.** رویداد در همان تراکنش نوشته می‌شود؛ relay با `FOR UPDATE SKIP LOCKED` + اجاره (lease) تحویل می‌دهد؛ اعلان با id قطعی ⇒ ایدمپوتنت. ۸ تلاش ⇒ DEAD + هشدار.
4. **Maker/Checker.** تأیید «یک‌بارمصرف» برای «یک اقدام» (و برای ثبت دستی، «همان مرجع»). `checker ≠ maker` علاوه بر کد با CHECK ی DB اجبار می‌شود.
5. **OpenAPI از Zod ی واقعی** (نه decorator های جدا): مستند و اعتبارسنجی یک منبع دارند. coverage با تست ratchet کنترل می‌شود؛ client ی تایپ‌شده‌ی فرانت از همان سند ساخته می‌شود.

## پیامدها
- حداقل ۲ ادمین لازم است (یا `REFUND_DUAL_APPROVAL=false` با پذیرش ریسک).
- تغییر نقش/تعلیق: درخواست بعدی ۴۰۱ می‌شود و کلاینت با refresh توکن تازه می‌گیرد. مقایسه با دقت میلی‌ثانیه (claim ی `ims`) انجام می‌شود تا refresh بلافاصله پس از ابطال معتبر بماند.
- اعلان‌ها تا ~۵ ثانیه تأخیر می‌گیرند (به‌جای «احتمال گم‌شدن»).
