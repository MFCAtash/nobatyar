# فاز ۸ — پرونده‌ی سلامت، triage، نظر دوم، SOAP و نسخه‌نویسی

بر پایه‌ی فاز ۷. جدول‌های `triage_sessions` و `second_opinions` از فاز ۱ فقط «استخوان‌بندی» بودند؛ این فاز آن‌ها را کامل و ۴ جدول تازه اضافه می‌کند.

## ۱) چه چیزی ساخته شد

| قابلیت | API | UI | تضمین کلیدی |
|---|---|---|---|
| **پرونده‌ی سلامت (بازنویسی)** | `/records/*` | `/records` | همه با `withContext` (RLS)، AAD درست، Audit خواندنِ غیرمالک، **اصلاح حفره‌ی `objectKey`** |
| **پروفایل سلامت** (حساسیت/زمینه‌ای/دارو) | `GET·PUT /me/health-profile`، `GET /appointments/:id/health-profile` | `/health-profile` | رمزنگاری؛ پزشک فقط با نوبت فعال/۹۰ روز اخیر (RLS) + Audit |
| **Triage** | `GET /triage/catalog`، `POST /triage/flags`، `POST /triage`، `GET /triage[/:id]` | `/triage` | موتور قطعی بدون LLM؛ نتیجه رمزنگاری‌شده؛ ۲۰ اجرا/ساعت |
| **SOAP** | `GET·PUT /appointments/:id/soap`، `POST …/soap/sign`، `POST …/soap/addenda` | `/appointments/:id/soap` | امضا = تغییرناپذیر (تریگر)؛ الحاقیه append-only؛ قفل خوش‌بینانه با `version` |
| **خلاصه‌ی ویزیت** | `GET /appointments/:id/visit-summary` | کارت «پس از ویزیت» | جدول جدا ⇒ RLS مرز ستونی می‌سازد: بیمار هرگز SOAP را نمی‌خواند |
| **نسخه** | `POST·GET /appointments/:id/prescriptions`، `GET /prescriptions[/:id]`، `POST /prescriptions/:id/cancel`، `GET /prescriptions/verify` (عمومی) | `/prescriptions`، `/appointments/:id/prescriptions` | تغییرناپذیر؛ ابطال+صدور مجدد؛ هشدار حساسیت؛ شماره `NV-XXXX-XXXX` + کد HMAC |
| **نظر دوم** | `/second-opinions/*` | `/second-opinions`، `/appointments/:id/second-opinion` | ماشین‌وضعیت مهلت‌دار (۴۸ ساعت پذیرش، ۷۲ ساعت پاسخ)، اشتراک پرونده موقت، job انقضا |

## ۲) تصمیم‌های طراحی

- **منطق خالص جدا از I/O** (مثل فاز ۷): `triage-engine`، `second-opinion-policy`، `soap-policy`، `prescription-policy`، `health-profile`، `records-policy` — بدون وابستگی، قابل‌تست و قابل‌بازبینی بالینی. سرویس‌ها فقط «حقایق» را از DB می‌گیرند و تصمیم را به این توابع می‌سپارند.
- **Triage «هوشمند» ولی ایمن:** قواعد کاتالوگ‌محور + پرچم‌های قرمز؛ قراردادها با تست‌های ویژگی‌محور قفل شده‌اند: (۱) هر پرچم EMERGENCY ⇒ EMERGENCY، (۲) یکنواختی (افزودن اطلاعات فوریت را کم نمی‌کند)، (۳) `mergeEnhancement` اجازه‌ی اتصال آیندهٔ LLM را می‌دهد ولی فقط می‌تواند فوریت را **بالا** ببرد. LLM عمداً وصل نشده: ارسال داده‌ی سلامت به سرویس بیرونی به رضایت صریح و قرارداد پردازش داده نیاز دارد.
- **مرز ستونی با جدول جدا:** RLS مرز ردیفی است؛ برای اینکه بیمار فقط «خلاصه» را ببیند، خلاصه در `visit_summaries` جدا منتشر می‌شود.
- **حریم خصوصی نظر دوم:** پزشک دوم فقط payload نوشته‌ی بیمار (+ سن/جنسیت اختیاری)، پرونده‌های صراحتاً به‌اشتراک‌گذاشته و (اختیاری) خلاصه‌ی ویزیت را می‌بیند. اشتراک‌ها با رد/لغو/انقضا لغو می‌شوند (پس از commit، با زمینه‌ی SYSTEM؛ انقضای طبیعی اشتراک پشتوانه است).
- **ماشین‌وضعیت دوبار:** یک‌بار در کد (`planSoAction`) و یک‌بار در DB (تریگر) — «چه کسی» هم اجبار می‌شود (فقط پزشک ACCEPT/ANSWER، فقط بیمار CANCEL، فقط SYSTEM EXPIRE).

## ۳) راه‌اندازی

```bash
cd apps/api
pnpm db:phase8          # مهاجرت schema + اعمال prisma/sql/phase8.sql (RLS، تریگرها، grants)
pnpm db:seed            # تخصص‌های جدید (داخلی، مغز و اعصاب، …) هم‌خوان با triage
```
`.env`: `SOAP_EDIT_WINDOW_DAYS` (پیش‌فرض ۷). ⚠️ `second_opinions` باید خالی باشد (تا فاز ۷ کدی در آن نمی‌نوشت؛ ستون‌های NOT NULL جدید اضافه می‌شوند).

## ۴) راستی‌آزمایی (صادقانه)

در محیط ساخت، نصب پکیج‌ها (شبکه) ممکن نبود؛ بنابراین:

- ✅ **۶۳ تست منطق خالص** اجرا و سبز شد (triage ۲۰، نظر دوم ۱۲، SOAP ۱۰، نسخه ۱۱، پروفایل ۴، رکوردها ۲، کمکی‌های UI ۴) و ماژول‌های خالص با `tsc --strict` بدون خطا هستند.
- ✅ همه‌ی فایل‌های جدید API از نظر **نحوی** وارسی شدند.
- ❌ **اجرا نشده:** `tsc` کامل پروژه (Nest/Prisma/Zod)، `prisma migrate`، `phase8.sql` روی Postgres واقعی، تست‌های یکپارچه، `next build`. **اولین کار شما:** `pnpm i && pnpm -r typecheck && pnpm -r test && pnpm db:phase8` و رفع احتمالی خطاهای تایپ.
- پیشنهاد: افزودن تست یکپارچه‌ی RLS برای: بیمار ⇏ `soap_notes`؛ پزشک دوم ⇏ `patient_profiles`؛ جهش امضاشده/نسخه رد می‌شود؛ گذارهای غیرمجاز نظر دوم رد می‌شود (الگوی `test/` فاز ۷).

## ۵) محدودیت‌ها و کارهای باز

1. **بازبینی بالینی الزامی:** کاتالوگ triage، شماره‌های اضطراری و فهرست هم‌گروهی دارویی باید توسط پزشک/داروساز بازبینی شود؛ هشدار حساسیت heuristic است.
2. **نسخه‌ی الکترونیک ملی (سپاس/تأمین‌اجتماعی)** وصل نیست؛ راستی‌آزمایی عمومی فقط اعتبار را می‌گوید. اتصال به آن فاز جدا می‌خواهد.
3. **پرداخت نظر دوم** نیست (جدول `payments` ۱‑به‑۱ با نوبت است)؛ MVP رایگان و با اختیار پزشک.
4. **ضمیمه‌های SOAP/نسخه PDF** ندارد (چاپ مرورگر).
5. **مشکلات باقی‌مانده از فاز ۵/۶** که در این فاز دست‌نخورده ماندند: `compare.controller` به فیلدهای ناموجود (`city`، `onlineVisit`، `availabilityRules`) ارجاع می‌دهد؛ `notifications`/`family_members` RLS ندارند (`NotificationService.push` بدون context است)؛ این‌ها پیش از فاز ۹ باید در یک «فاز ۸.۵» بسته شوند.
6. اعلان‌ها هیچ داده‌ی سلامت ندارند (فقط شناسه و متن عمومی).

## ۶) ورودی فاز ۹
Redis pub/sub برای SSE چندنمونه‌ای (اعلان‌های جدید این فاز هم از همان مسیرند)، load test روی `/triage` (rate-limit) و `/prescriptions/verify`، و تست‌های RLS یکپارچه در CI.

## ۷) اصلاحات پس از بازبینی (۸.۵-الف)

- **پروفایل سلامت برای پزشک:** `GET /appointments/:id/health-profile` اکنون `exists` برمی‌گرداند. `exists=false` یعنی «ثبت نشده یا برای شما نامرئی»، نه «بدون حساسیت». UI (`AllergyBanner`) همیشه یکی از چهار حالت را نشان می‌دهد: بارگذاری‌نشد، ثبت‌نشده، بدون حساسیت ثبت‌شده، فهرست. پاسخ صدور نسخه `allergyProfileOnFile` هم دارد.
- **هشدار حساسیت:** نام‌های تجاری رایج، گروه اپیوئیدها، سولفونامیدهای غیرآنتی‌بیوتیک و هشدار «واکنش متقاطع» پنی‌سیلین↔سفالوسپورین اضافه شد. فهرست همچنان ناقص و heuristic است و UI/API متن `ALLERGY_CHECK_NOTE_FA` را نشان می‌دهند. بازبینی داروساز لازم است.
- **proxy و worker:** `TRUST_PROXY_HOPS` و `ENABLE_WORKERS` در `.env.example` آمدند و `main.ts` در production هشدار می‌دهد.
